Architecture Deep Dive

3-Tier 종합 아키텍처 & 데이터 통신 흐름

실습 6 & 7 핵심 구조

웹 브라우저의 HTTP 요청이 들어왔을 때, 1층 문지기(Nginx)가 요청을 받고 2층 주방(Node.js WAS)이 3층 비밀 금고(MariaDB)에서 데이터를 꺼내오는 전체 여정을 시각화한 구조도입니다.

1계층 Web (Nginx)

유일하게 외부 포트(80) 개방. 손님을 맞이하고 정적 파일 서빙 및 비즈니스 요청을 WAS로 안전하게 전달(Reverse Proxy)합니다.

2계층 WAS (Node.js)

외부 포트 미개방 (보안). 오직 내부망(3tier-net) 안에서만 통신하며, 계산·인증·DB 쿼리 로직을 실행합니다.

3계층 DB (MariaDB)

외부 노출 차단 + 볼륨 마운트. 해킹 위협을 완벽히 차단하고, 컨테이너가 죽어도 mariadb-data 볼륨으로 데이터를 지킵니다.

Intuitive Learning

비전공자를 위한 핵심 비유 8선

📦 ↔ 🏠

1. 이미지(Image) vs 컨테이너(Container)

이미지: 요리 레시피가 담긴 밀키트 / 게임 설치 CD (절대 변하지 않는 읽기 전용 설계도).
컨테이너: 밀키트를 뜯어서 냄비에 넣고 불을 켠 실제 실행 상태(Process). 1개의 밀키트로 100개의 냄비를 동시에 끓일 수 있습니다.

🏢 ↔ 📦

2. 가상머신(VM) vs 도커 컨테이너

가상머신: Mac 안에 무거운 윈도우 OS 커널을 통째로 띄우는 단독주택 (부팅 1분, 수십 GB 낭비).
도커: 내 컴퓨터의 심장(리눅스 커널)을 공유하며 벽(격리)만 쳐서 방을 나눈 아파트 (부팅 0.1초, 수십 MB).

🕶️

3. 네임스페이스 (Namespace)

프로세스에게 "세상에 너 혼자밖에 없어!"라고 믿게 만드는 가상화 투명 망토입니다. 컨테이너 안에서는 자기가 PID 1번(대장)인 줄 착각하지만, 호스트 컴퓨터 입장에선 수많은 프로세스 중 하나일 뿐입니다.

⚖️

4. Cgroups (컨트롤 그룹)

"1번 방은 CPU 최대 50%, RAM 512MB까지만 써!"라고 선을 긋는 자원 배급소. 한 컨테이너의 메모리 폭주(누수)로 컴퓨터 전체가 다운되는 사고를 완벽히 막아냅니다.

🚪

5. 포트 포워딩 (-p 8080:80)

아파트 로비의 인터폰 호수 연결과 같습니다. -p 8080:80은 내 Mac의 8080번 인터폰을 누르면 컨테이너 방의 80번 문으로 손님을 텔레포트시켜 줍니다.

🗄️

6. 도커 볼륨 (Volume, -v)

컨테이너는 언제든 버릴 수 있는 종이컵입니다. 죽어도 남겨야 하는 DB 파일은 컴퓨터의 영구 외장 금고(볼륨)에 보관하여 컨테이너가 폭파되어도 데이터를 보존합니다.

📻

7. 브리지 사설망 & 사설 DNS

컨테이너들만의 비밀 무전기 채널. 복잡한 IP 주소(172.21.0.3) 대신 컨테이너 이름(db, was)만 부르면 도커 내부 DNS가 알아서 통화를 즉시 연결해 줍니다.

🏗️

8. 멀티스테이지 빌드

공사가 끝나면 무거운 타워크레인은 철거하고 완성된 아파트만 입주하기. 빌드 찌꺼기(컴파일러, 캐시)를 버려 용량을 1.78GB → 185MB로 10분의 1 압축합니다.

구분 리눅스 커널 기술 실제 엔지니어링 역할 미적용 시 위험
시야 격리 Namespace PID(프로세스), NET(네트워크 veth), MNT(마운트), UTS(호스트명), IPC, USER를 완전 독립 다른 컨테이너의 프로세스 강제 종료 또는 네트워크 패킷 탈취

Step-by-Step Curriculum

집중 실습 1~9 총정리 & 검증 가이드

01

단순 컨테이너 생성과 생명주기 (hello-world)

교재 4쪽

도커가 인터넷에서 이미지를 Pull 받아 컨테이너를 생성하고, 화면에 편지를 출력한 뒤 스스로 정상 종료(Exited 0)하는 기본 생명주기를 관찰합니다. 

# 1. hello-world 컨테이너 실행 (자동 Pull 및 출력)
docker run hello-world

# 2. 실행 중 목록 조회 (비어 있음!)
docker ps

# 3. 종료된 컨테이너까지 전체 조회 (-a)
docker ps -a
Exited (0)의 비밀: 숫자 0은 에러 없이 정상적으로 임무를 완수하고 은퇴했다는 뜻입니다.
02

Nginx 웹서버 실행 및 포트 포워딩 (-d, -p 8080:80)

교재 5쪽

백그라운드 모드(-d)로 24시간 살아있는 웹서버를 띄우고, 포트 포워딩(-p 8080:80)으로 내 브라우저와 컨테이너를 연결합니다. 

# 백그라운드(-d) 및 포트 연결(-p)로 실행
docker run -d -p 8080:80 --name web nginx

# 브라우저에서 http://localhost:8080 접속 후 실시간 로그 확인
docker logs web

# 정리
docker rm -f web
03

Dockerfile로 나만의 Node.js 이미지 빌드

교재 6쪽

FROM(바닥판), COPY(내 코드), CMD(시동 명령) 3대 뼈대로 내가 짠 코드(app.js)를 이미지로 구워냅니다. 

# Dockerfile (3줄 레시피)
FROM node:18-alpine
COPY app.js .
CMD ["node", "app.js"]
# 빌드 및 실행 (자동 청소 --rm)
docker build -t my-node-app .
docker run --rm my-node-app
04

볼륨(Volume) - 데이터 영속화와 삭제 검증

교재 7~9쪽

컨테이너를 삭제(docker rm -f)해도 MariaDB 회원 데이터(alice, bob, carol)가 mariadb-data 볼륨 덕분에 100% 보존됨을 입증합니다. 

# 1. 영구 볼륨 생성 & 컨테이너 실행
docker volume create mariadb-data
docker run -d --name mariadb -e MYSQL_ROOT_PASSWORD=password123 -e MYSQL_DATABASE=skala -e MYSQL_USER=user -e MYSQL_PASSWORD=password123 -p 3306:3306 -v mariadb-data:/var/lib/mysql mariadb:11

# 2. 컨테이너 삭제 후 같은 볼륨으로 재기동 검증!
docker rm -f mariadb
docker run -d --name mariadb -e MYSQL_ROOT_PASSWORD=password123 -e MYSQL_DATABASE=skala -e MYSQL_USER=user -e MYSQL_PASSWORD=password123 -p 3306:3306 -v mariadb-data:/var/lib/mysql mariadb:11
docker exec mariadb mariadb -u user -ppassword123 skala -e "SELECT * FROM users;"
05

Harbor Registry Push & Pull (g124 태깅)

교재 10~11쪽

사내 엔터프라이즈 Harbor 저장소에 내 고유 식별자(skala-webserver-g124)를 붙여 Push하고, 로컬에서 지운 뒤 Pull로 내려받아 8081 포트로 검증합니다. 

# 1. 태그 부착 & 업로드 (Push)
docker tag skala-webserver:1.0.0 harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0
docker push harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0

# 2. 로컬 이미지 삭제 후 순수 Harbor에서 Pull 받아 실행
docker rmi harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0
docker pull harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0
docker run -d -p 8081:80 --name from-harbor harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0
06

3-Tier (Web-WAS-DB) 수동 네트워크 구성

교재 12~17쪽

전용 브리지 네트워크(3tier-net) 안에서 IP 대신 컨테이너 이름(DNS)으로 3개 컨테이너가 서로를 찾아가게 만듭니다. 

# 1. 가상 사설망 생성
docker network create 3tier-net

# 2. DB 및 WAS 실행 (포트 미개방으로 보안 유지)
docker run -d --name mariadb-3tier --network 3tier-net -v $(pwd)/db:/docker-entrypoint-initdb.d mariadb:11
docker run -d --name was --network 3tier-net was-app

# 3. Nginx 실행 (유일하게 외부 포트 80 개방)
docker run -d --name nginx --network 3tier-net -p 80:80 -v $(pwd)/web:/etc/nginx/conf.d nginx

# 4. 연동 결과 확인
curl -s http://localhost/users
07

Docker Compose 3-Tier 자동 오케스트레이션

교재 18~23쪽

명령어 7개를 칠 필요 없이 compose.yaml 단 한 장과 healthcheck로 DB가 준비될 때까지 기다렸다가 완벽하게 가동합니다. 

# compose.yaml
services:
  web:
    image: nginx:alpine
    ports: ["80:80"]
    volumes: ["./web/default.conf:/etc/nginx/conf.d/default.conf:ro"]
    depends_on: [was]
  was:
    build: ./was
    depends_on:
      db:
        condition: service_healthy
  db:
    image: mariadb:10.11
    volumes: ["db-data:/var/lib/mysql", "./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro"]
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect"]
      interval: 5s
      retries: 10
volumes:
  db-data:
# 실행 및 종료
docker compose up -d       # 일괄 빌드 및 기동
docker compose ps          # 상태 및 헬스체크 확인
docker compose down -v     # 볼륨까지 일괄 삭제
08

스케일아웃 (--scale was=3) 및 무중단 로드밸런싱

교재 24~27쪽

WAS 서버를 3벌로 늘리고, 1대가 고의로 죽어도 Nginx의 proxy_next_upstream 설정 덕분에 손님 요청이 끊기지 않는 고가용성(HA)을 검증합니다. 

# 1. WAS를 즉시 3대로 수평 확장 (Scale-Out)
docker compose up -d --scale was=3
docker compose exec web nginx -s reload

# 2. 1대를 강제 종료해도 다른 서버가 즉시 응답하는 무중단 Failover 확인
docker stop 08_scale_and_loadbalancing-was-2
for i in $(seq 1 15); do curl -s -o /dev/null -m 5 -w '%{http_code}/%{time_total}s\n' localhost/whoami; done
09

이미지 다이어트 대회 (1.78GB → 185MB)

교재 28~32쪽

Alpine 베이스 교체, 캐시 순서 최적화, Multi-Stage Build를 거쳐 1.78GB 이미지를 185MB로 10분의 1 압축시키는 마법을 완성합니다.

도커 명령어 & Dockerfile 마스터 사전

명령어 / 키워드 기능 설명 실무 꿀팁
docker ps -a 모든 컨테이너(종료된 것 포함) 목록 조회 STATUS: Exited(0)은 정상 완료를 의미

docker volume prune 안 쓰는 고아 볼륨 일괄 청소 컨테이너 삭제 후 남은 쓰레기 디스크 절약
docker compose up -d --scale was=3 서비스 인스턴스를 즉시 3대로 확장 무중단 고가용성 로드밸런싱 실현
FROM node:18-alpine AS builder 멀티스테이지 1단계 빌드 환경 선언 최종 산출물만 2단계로 복사하여 10분의 1 경량화
