🏛️ PART 1. 3-Tier 종합 아키텍처 & 데이터 흐름도

웹 브라우저의 인입부터 리버스 프록시(Nginx), 백엔드 비즈니스 로직(WAS), 영구 데이터베이스(MariaDB & Volume)까지의 전체 연결 경로를 시각화한 실무 구조도입니다.

🗺️ PART 2. 비전공자 맞춤 현실 비유 8선
📦

1. 이미지 vs 🏠 컨테이너

이미지: 밀키트 / 게임 설치 CD (절대 변하지 않는 읽기 전용 설계도).
컨테이너: 밀키트를 냄비에 넣고 가스레인지를 켠 실제 실행 상태(Process).

🏢

2. 가상머신(VM) vs 📦 도커

가상머신: Mac 안에 무거운 OS 전체를 띄우는 단독주택 (부팅 1분, 수십 GB 낭비).
도커: 호스트 커널을 공유하고 벽(격리)만 쳐서 방을 나눈 아파트 (부팅 0.1초, 수십 MB).

🕶️

3. 네임스페이스 (Namespace)

프로세스에게 "세상에 너 혼자밖에 없어!"라고 믿게 만드는 가상화 투명 망토. 컨테이너 안에서는 자기가 PID 1번(대장)인 줄 착각합니다.

⚖️

4. Cgroups (컨트롤 그룹)

"1번 방은 CPU 최대 50%, RAM 512MB까지만 써!"라고 선을 긋는 자원 배급소. 메모리 폭주로 컴퓨터 전체가 뻗는 것을 방지합니다.

🚪

5. 포트 포워딩 (-p)

아파트 로비의 인터폰 호수 연결과 같습니다. -p 8080:80은 내 Mac의 8080번 인터폰을 누르면 컨테이너의 80번 문으로 연결해 줍니다.

🗄️

6. 도커 볼륨 (Volume, -v)

컨테이너는 언제든 버릴 수 있는 종이컵입니다. 죽어도 남겨야 하는 DB 파일은 컴퓨터의 영구 외장 금고(볼륨)에 보관합니다.

📻

7. 브리지 사설망 & DNS

컨테이너들만의 비밀 무전기 채널. 복잡한 IP 주소 대신 컨테이너 이름(db, was)만 부르면 도커가 알아서 통화를 연결해 줍니다.

🏗️

8. 멀티스테이지 빌드

공사가 끝나면 무거운 타워크레인은 철거하고 완성된 아파트만 입주하기. 빌드 찌꺼기를 버려 용량을 1.78GB → 185MB로 압축합니다.

🔬 PART 3. 심화 CS: 리눅스 커널 격리 메커니즘
구분 리눅스 커널 기능 실제 역할 미적용 시 발생 위험
시야 격리 Namespace (PID, NET, MNT, UTS, IPC, USER) 프로세스 트리, 가상 네트워크 카드(veth), 파일시스템 마운트 지점을 완전히 독립시킴. 다른 컨테이너의 프로세스를 강제 종료하거나 패킷 탈취 사고 발생.
자원 제한 cgroups (CPU, Memory, blkio) 컨테이너별 하드웨어 최대 사용 상한선을 지정하고 초과 시 OOM Killer로 통제. 특정 컨테이너의 메모리 누수로 서버 전체가 다운됨.
계층 스토리지 OverlayFS (Copy-on-Write) 하위 읽기 전용 이미지 레이어 위에 얇은 쓰기 층(UpperDir)을 얹어 변경분만 기록. 컨테이너 생성마다 수 GB의 OS 파일 전체를 복사하여 디스크가 낭비됨.
📚 PART 4. 집중 실습 1~9 총정리 & 검증 노트
01 단순 컨테이너 생성과 생명주기 (hello-world)

컨테이너가 생성되고, 인사말을 출력하고, 스스로 정상 종료(Exited 0)하는 생명주기를 관찰합니다.

# 1. hello-world 컨테이너 실행 (없으면 Docker Hub에서 자동 다운로드)
docker run hello-world

# 2. 실행 중인 컨테이너 확인 (비어 있음!)
docker ps

# 3. 종료된(Exited) 컨테이너까지 전체 확인
docker ps -a
Exited (0)의 비밀: 숫자 0은 에러 없이 정상적으로 임무를 완수하고 은퇴했다는 뜻입니다.
02 Nginx 웹서버 실행 및 포트 포워딩 (-d, -p 8080:80)

24시간 백그라운드로 켜두고 외부 브라우저와 통신하는 웹서버의 기본 원리를 실습합니다.

# 백그라운드(-d) 및 포트포워딩(-p 8080:80)으로 Nginx 실행
docker run -d -p 8080:80 --name web nginx

# 브라우저 http://localhost:8080 접속 후 로그 확인
docker logs web

# 정리
docker rm -f web
03 Dockerfile로 나만의 Node.js 이미지 빌드

FROM, COPY, CMD 3대 뼈대로 내가 짠 코드(app.js)를 이미지로 구워냅니다.

# Dockerfile
FROM node:18-alpine
COPY app.js .
CMD ["node", "app.js"]

# 빌드 및 자동 청소(--rm) 실행
docker build -t my-node-app .
docker run --rm my-node-app
04 볼륨(Volume) - 데이터 영속화와 삭제 검증

컨테이너를 삭제해도 MariaDB의 회원 데이터가 볼륨(mariadb-data) 덕분에 100% 보존됨을 확인합니다.

# 1. 영구 볼륨 생성
docker volume create mariadb-data

# 2. 볼륨 마운트하여 MariaDB 실행
docker run -d --name mariadb -e MYSQL_ROOT_PASSWORD=password123 -e MYSQL_DATABASE=skala -e MYSQL_USER=user -e MYSQL_PASSWORD=password123 -p 3306:3306 -v mariadb-data:/var/lib/mysql mariadb:11

# 3. 컨테이너 삭제 후 같은 볼륨으로 재기동해도 데이터 생존 확인!
docker rm -f mariadb
docker run -d --name mariadb -e MYSQL_ROOT_PASSWORD=password123 -e MYSQL_DATABASE=skala -e MYSQL_USER=user -e MYSQL_PASSWORD=password123 -p 3306:3306 -v mariadb-data:/var/lib/mysql mariadb:11
docker exec mariadb mariadb -u user -ppassword123 skala -e "SELECT * FROM users;"
05 Harbor Registry Push & Pull (g124 태깅)

사내 중앙 저장소(Harbor)에 내 고유번호 태그(g124)를 붙여 업로드하고 원격에서 다시 받아옵니다.

# 1. 태그 달기 & Harbor Push
docker tag skala-webserver:1.0.0 harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0
docker push harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0

# 2. 내 PC에서 지우고 Harbor에서 다시 Pull 받아 실행
docker rmi harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0
docker pull harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0
docker run -d -p 8081:80 --name from-harbor harbor.skala-gj.com/skala-gj4/skala-webserver-g124:1.0.0
06 3-Tier (Web-WAS-DB) 수동 네트워크 구성

가상 네트워크(3tier-net) 안에서 IP 대신 컨테이너 이름(DNS)으로 3계층을 연결합니다.

# 1. 네트워크 생성
docker network create 3tier-net

# 2. DB 및 WAS 실행 (포트 미개방으로 보안 격리)
docker run -d --name mariadb-3tier --network 3tier-net -v $(pwd)/db:/docker-entrypoint-initdb.d mariadb:11
docker run -d --name was --network 3tier-net was-app

# 3. Nginx 실행 (80 포트 유일 개방)
docker run -d --name nginx --network 3tier-net -p 80:80 -v $(pwd)/web:/etc/nginx/conf.d nginx

# 4. 연동 확인
curl -s http://localhost/users
07 Docker Compose 3-Tier 자동 오케스트레이션

compose.yaml 단 한 장과 healthcheck로 DB가 준비될 때까지 기다렸다가 완벽하게 가동합니다.

# 1. 한 번에 전체 3-Tier 빌드 및 기동
docker compose up -d

# 2. 헬스체크 및 서비스 상태 확인
docker compose ps

# 3. 종료 (볼륨 유지) vs 완전 초기화 (볼륨 삭제)
docker compose down
docker compose down -v
08 서버 증설 (--scale was=3) 및 무중단 로드밸런싱

WAS를 3대로 증설하고, 1대가 고의로 죽어도 Nginx failover 덕분에 무중단 서비스됨을 입증합니다.

# 1. WAS를 3대로 수평 확장
docker compose up -d --scale was=3
docker compose exec web nginx -s reload

# 2. 1대가 갑자기 죽어도 다른 살아있는 WAS로 즉시 토스 (무중단 200 OK)
docker stop 08_scale_and_loadbalancing-was-2
for i in $(seq 1 15); do curl -s -o /dev/null -m 5 -w '%{http_code}/%{time_total}s\n' localhost/whoami; done
09 이미지 다이어트 대회 (1.78GB → 185MB)

Alpine 베이스 교체, 캐시 순서 최적화, Multi-Stage Build를 거쳐 10분의 1로 경량화합니다.

버전 최적화 기법 이미지 크기 재빌드 시간
v1 기본 node:18 (Debian 풀버전) 1.78 GB 45.2초
v2 초경량 node:18-alpine 베이스 교체 399 MB 32.9초
v3 package.json 먼저 복사 + --omit=dev 321 MB 6.5초
v4 멀티스테이지 빌드 (AS builder) 185 MB 0.79초 (최강!)
💻 PART 5. 핵심 Docker 명령어 치트시트
명령어 기능 설명 실무 꿀팁
docker ps -a 모든 컨테이너 목록 조회 STATUS: Exited(0)은 정상 종료를 의미
docker run -d -p 80:80 백그라운드 포트 연결 실행 -d가 없으면 터미널 창을 독점당함
docker exec -it [이름] sh 컨테이너 내부 셸 접속 -it가 대화형 키보드 입력을 켬
docker volume prune 안 쓰는 고아 볼륨 일괄 청소 컨테이너 삭제 후 남은 쓰레기 정리
docker compose up -d --scale was=3 서비스 즉시 3대로 확장 무중단 고가용성 로드밸런싱 실현
